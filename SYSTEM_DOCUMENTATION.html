Section 1
System Overview
1.1 Purpose of the System

MonkiHub is a full-stack web-based team collaboration and task management platform designed specifically for managing Virtual Assistants (VAs) and remote teams. It provides a centralized workspace where administrators can assign tasks, communicate with team members in real-time, track work progress, and process payments — all within a single web application.

The system was built as a final project for the Web-Based Systems course, demonstrating the integration of modern web technologies including Apache Kafka as a message broker, XML-based data storage with XSLT transformations, real-time communication via Socket.IO, and automated background scripting.

Core Mission: Replace manual task tracking and scattered communication tools with a unified platform that demonstrates enterprise-level messaging patterns (producer-consumer) and structured data management (XML/XSLT).

1.2 Target Users
Role Description Permissions
Super Admin The highest-level administrator. Only one Super Admin exists (default: admin). Manages all users including other admins. Full access — create admins, manage tasks, delete users, view all logs
Admin Team managers or supervisors. Created by the Super Admin. Responsible for assigning tasks and approving work. Create/manage tasks, approve/reject submissions, process payments, view logs
User (VA) Virtual Assistants or team members. Register via the public registration form. View assigned tasks, submit proof of work, send messages, request payments
1.3 Key Capabilities
  • Real-time messaging powered by Apache Kafka producer-consumer pattern
  • Task management with Kanban board (To Do → In Progress → Pending Review → Done)
  • Proof-of-work submission with admin approval/rejection workflow
  • Payment request system supporting GCash, Maya, Bank Transfer, and PayPal
  • XML data storage with XSLT transformations for structured data display
  • Background automation scripts for notifications, archiving, and reporting
  • Calendar view with task due date tracking and color-coded status indicators
  • Security features including rate limiting, IP blacklisting, and CSP headers
  • Mobile-responsive design with floating action button for mobile task creation
  • Cloud image storage via Cloudinary for avatars, task references, and proof uploads

Feature Descriptions
3.1 Messaging System — Apache Kafka

MonkiHub uses Apache Kafka (via Redpanda Cloud or local Docker) as the message broker for all direct messages between users. This implements the classic producer-consumer pattern used in real-world systems like Slack, WhatsApp, and Discord.

How it works:
  1. User types a message and clicks Send → frontend calls POST /api/messages
  2. messageController.js calls brokerService.publishMessage() which sends the message to the Kafka topic monkihub_messages
  3. consumer.js (running as a separate process) subscribes to the topic and receives the message
  4. The consumer saves the message to messages.xml and emits it via Socket.IO to the recipient's browser
  5. The recipient sees the message appear in real-time without refreshing

Demo Feature: If consumer.js is stopped from the Script Manager panel, messages will NOT be delivered. Starting it again resumes delivery. This visually demonstrates the broker dependency.

Kafka Configuration:

3.3 XML Parsing Method — DOM Parsing with xml2js

MonkiHub uses the xml2js Node.js library for DOM-based XML parsing. The library converts XML files into JavaScript objects, allowing full CRUD operations on the data without a traditional database.

Parsing Implementation (xmlService.js):
const xml2js = require('xml2js'); const parser = new xml2js.Parser(); // XML → JS Object const builder = new xml2js.Builder({ // JS Object → XML xmldec: { version: '1.0', encoding: 'UTF-8' } }); // READ: Parse XML file into JavaScript object async function readXml(filename) { const content = await fs.readFile(path.join(DATA_DIR, filename), 'utf8'); return parser.parseStringPromise(content); // Result: { tasks: { task: [ { $: {id:'...'}, title:['...'], ... } ] } } } // WRITE: Convert JS object back to XML and save async function writeXml(filename, data) { const xml = builder.buildObject(data); await fs.writeFile(path.join(DATA_DIR, filename), xml, 'utf8'); }
How xml2js Parses XML Attributes:

xml2js maps XML attributes to the $ property and element text content to arrays:

// XML: <user id="user-abc"><username>admin</username></user> // Parsed JS object: { $: { id: "user-abc" }, // XML attributes → $ object username: ["admin"], // Element text → array role: ["admin"], isSuperAdmin: ["true"] }
CRUD Operations via DOM Parsing:
  • Create: Read XML → push new object to array → write back to file
  • Read: Parse XML → filter/find by field values
  • Update: Parse XML → find index → modify fields → write back
  • Delete: Parse XML → filter out target → write back

Section 4
Technical Explanation
4.1 How Each Requirement Was Implemented
✅ Requirement 1: Messaging System with Message Broker (Kafka)

Implementation: Apache Kafka via Redpanda Cloud (or local Docker). Producer in brokerService.js, Consumer in scripts/consumer.js.

When a user sends a message, messageController.js calls publishMessage() which uses the KafkaJS library to produce a message to the monkihub_messages topic. The consumer script runs as a separate Node.js process, subscribes to the same topic, and for each message received: (1) parses the JSON payload, (2) saves it to messages.xml via MessageModel.create(), and (3) emits a consumer:deliver Socket.IO event back to the main server, which then forwards it to the recipient's browser via user:<username> rooms.

The system auto-detects whether Kafka is running locally (no SSL/SASL) or in the cloud (SCRAM-SHA-256 authentication). If Kafka is completely unavailable, an in-memory fallback delivers messages directly without the broker.

✅ Requirement 2: XML Data Handling

Implementation: 6 XML files in backend/data/. All CRUD operations read/write XML using xml2js.

Every data entity (users, tasks, messages, payments, logs, archive) is stored as a structured XML file with meaningful element names and hierarchy. The xmlService.js service provides centralized readXml() and writeXml() functions used by all model files. Data validity is maintained by always reading the full file, modifying the in-memory object, and writing the complete file back — ensuring the XML remains well-formed at all times.

The users.xml file is tracked in Git so that user accounts persist across cloud deployments on Render. Other data files are excluded from Git and reset on each deploy (ephemeral storage).

✅ Requirement 3: XML Parsing (DOM)

Implementation: xml2js library for DOM-based parsing. All models use parser.parseStringPromise().

The xml2js.Parser() instance converts XML files into a JavaScript object tree (DOM-like structure). Each model file (UserModel, TaskModel, etc.) uses this parsed object to perform CRUD operations:

  • findAll() — reads and maps all records to plain objects
  • findByUsername() / findById() — filters the parsed array
  • create() — pushes a new object and writes back to XML
  • update() — finds by index, modifies fields, writes back
  • delete() — filters out the target record, writes back
✅ Requirement 4: XSL/XSLT Transformations

Implementation: 3 XSLT files executed server-side via xslt3 CLI. Accessible in the XML Viewer panel.

The XML Viewer panel (accessible to all authenticated users) provides two views: Raw XML (plain text) and XSLT Output (transformed HTML table). When the XSLT view is selected, the server calls transformXslt() which runs the xslt3 Node.js package as a child process, passing the XML file and XSLT stylesheet. The resulting HTML is returned to the browser and rendered inline. Each XSLT file uses multiple XSLT elements: xsl:for-each, xsl:sort, xsl:choose, xsl:when, xsl:if, xsl:attribute, and xsl:value-of.

✅ Requirement 5: Scripting Languages (Node.js)

Implementation: 4 automation scripts in backend/scripts/. Managed via Script Manager UI.

All four scripts are standalone Node.js programs that can run independently of the main server. The scriptController.js uses Node's child_process.spawn() to start scripts as child processes, captures their stdout/stderr, and streams log lines to the browser via Socket.IO events (script:log:<name>). Scripts can be stopped by calling process.kill() on the child process PID.

✅ Requirement 6: Web Deployment

Implementation: Deployed on Render.com (free tier). Monitored 24/7 via UptimeRobot.

The application is deployed as a single Web Service on Render. The root package.json defines the build command (npm install) and start command (npm start → node backend/server.js). Environment variables (Kafka credentials, JWT secret, Cloudinary keys) are configured in Render's dashboard. UptimeRobot pings the URL every 5 minutes to prevent the free-tier instance from sleeping.

4.4 Challenges Encountered and Solutions
#ChallengeSolution
1 Dashboard hang after login — The dashboard froze because /auth/list required admin role. Regular users got a 403 error inside Promise.all(), crashing the entire dashboard load and leaving skeleton loaders permanently. Made the users fetch conditional: isAdmin ? apiCall('/auth/list') : Promise.resolve([]). Also created a separate listUsers endpoint that returns safe user data for all authenticated users (needed for chat).
2 Buttons not working (CSP blocking onclick handlers) — Helmet.js sets script-src-attr 'none' by default, which blocked all inline event handlers like onclick="login()" in the HTML. Added scriptSrcAttr: ["'unsafe-inline'"] to the Helmet CSP configuration to explicitly allow inline event handlers.
3 Stateful regex bug blocking random requests — The suspicious pattern detection middleware used regex with the /g flag (e.g., /on\w+\s*=/gi). JavaScript regexes with the g flag retain lastIndex between calls, causing alternating pass/fail on every other request. Removed the g flag from all patterns and simplified the pattern list to only match genuinely dangerous inputs (script tags, SQL injection, path traversal).
4 xml2js raw node access crash — Multiple controller functions called u.$.id and u.username[0] directly on raw xml2js nodes. When $ was undefined (e.g., for users without XML attributes), the app crashed with "Cannot read properties of undefined (reading 'id')". Standardized all data access through UserModel.findAll() which maps raw xml2js nodes to clean plain objects ({ id, username, role, ... }). All controllers now use these mapped objects.
5 User accounts lost on every Render deploy — Render's free tier uses ephemeral storage, wiping all files on each deployment. All user accounts created online were deleted every time the app was redeployed. Added users.xml back to Git tracking (removed from .gitignore). Now user accounts persist across deploys. Other data files (tasks, messages, etc.) remain ephemeral.
6 Super Admin role lost after fresh deploy — The admin seed function in xmlService.js created the admin user without the isSuperAdmin field. On a fresh deployment, the JWT token had isSuperAdmin: false, hiding the Create Admin button. Added isSuperAdmin: ['true'] to the seeded admin user object in initXmlFiles().
7 Kafka SSL/SASL errors on local development — The Kafka client was configured with SSL and SASL authentication for cloud use, but local Docker Kafka doesn't require authentication, causing connection failures. Added auto-detection: if KAFKA_BROKER contains localhost or 127.0.0.1, SSL and SASL are skipped. Cloud brokers use SCRAM-SHA-256 authentication.
8 CORS blocking all API requests on Render — The custom CORS middleware only allowed specific origins (localhost:3000 and env vars). On Render, the origin didn't match exactly, so no CORS headers were set, making every fetch() call fail silently. Simplified the CORS middleware to always set Access-Control-Allow-Origin to the request origin (or *), since the frontend is served from the same server.
